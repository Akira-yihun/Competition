# 评审记录与修订台账

> 本文件记录**多轮对抗式评审**的发现与处理（对应需求第 4 条："调用多个 agent，循环检查几次，确保回答的完善"）。
> 每条都可追溯到文件、章节与**可复现的证据**。
> 归档自检：`python3 reference/selfcheck.py` —— **78 项全绿**才算交付完成。

---

## 0. 评审设计

| 轮次 | 角色 | 目标 | 产出 |
|---|---|---|---|
| R1-A | **独立规则/协议审计员** | 从零核对任务书/接口文档/报文/Demo | 协议契约表（22 字段）、异常风险表、时序、数值事实表、**35 条开放问题**、Demo 差距表 |
| R1-B | **独立策略分析师**（不看我的草稿） | 从零推导目标函数与得分策略 | 目标逻辑树、三条得分线定量、行动预算、几何反推、选靶算法、经济模型、12 条反直觉洞察 |
| R1-C1 | **对抗式评审·策略** | 专找文档错误 | 4 严重 + 20 中等 + 17 轻微，含逐条原文核对 |
| R1-C2 | **对抗式评审·Loop 计划** | 专找设计缺陷 | 40+ 条，含 3 个"接平台必翻车"点 |
| R1-C3 | **对抗式评审·日志与加密** | 实测复现 | **27 条，含 5 个可复现 PoC**（12 个复现脚本） |
| R1-C4 | **需求覆盖与一致性审计** | 交叉核对 5 条需求与跨文档一致性 | 覆盖矩阵 + 30+ 处不一致 + 验收评分 |
| R2-D | **本机脚本复算** | 对高风险断言做机器验证 | 9 项，其中 **2 项推翻了 R1-A/B 的说法** |

**为什么这样设计**：只让一个 Agent 写、另一个读，容易变成互相表扬。因此 R1-A/B 是**独立推导**（不看草稿）、R1-C 是**对抗式**（明确要求找错）、R2-D 是**机器可验证**（不依赖任何 Agent 的措辞）。

# 03 · 对局日志格式与加密设计（fwlog v1.1）

> 目的：① 为"自动分析 / 归因 / 迭代"提供结构化、可回溯的日志；② 双方队伍**共用同一套日志接口**，但**任何一方都无法读取对方的日志**。
> **可执行规范（字节级真值）**：`reference/fwlog_crypto_ref.py`；**已知答案向量**：`reference/fwlog_kat.json`；**可运行样例**：`samples/`。
>
> **v1.1 说明**：v1.0 经对抗式评审（含可复现 PoC）发现 5 个严重缺陷（明文 blob、密钥可从产物提取、链不绑内容、崩溃重启写废日志、性能数字自相矛盾），
> 本版全部修正。修订台账见 `REVIEW.md`。**v1.0 的任何结论都不要再用。**

---

## 0. 结论速览

| 问题 | 方案 |
|---|---|
| 日志长什么样 | NDJSON，**一行一帧**；帧 = `{"h":头部, "c":密文, "t":MAC, "x":新链值}`；载荷是 `fwlog.event/1` 的规范化 JSON |
| 怎么加密 | 每 **(比赛,队伍,实例,半场,运行)** 一把密钥（HKDF-SHA256 从**队伍主密钥**派生）+ **HMAC-SHA256 计数器密钥流** + **Encrypt-then-MAC**；**仅标准库** |
| 为什么双方不能互看 | 接口/格式/代码完全相同，**唯一差别是各自持有的 `team_secret`** ⇒ 同一存储里两队的密文互不可解；连平台侧也**不需要也无法**解密（零信任） |
| **大对象（blob）会不会泄漏** | **不会**：v1.1 起 blob 也走同一加密帧（单帧文件），**不再有任何明文快照** |
| 篡改/插帧/换序/跨运行拼接 | **内容绑定累进链** `x_i = HMAC(K_mac, "CHAIN"‖chain_{i-1}‖seq‖len(aad)‖aad‖ct)` + `chain_0` 绑 `run_id` ⇒ 全部可检测（实测） |
| **尾部截断** | 链**检测不到**（如实说明）；靠**终结锚 anchor** `(run_id, count, first_chain, last_chain)` 检测，锚需落到**文件之外**（平台回执或 sidecar） |
| 崩溃重启 | **不换链**：`Writer.checkpoint()` / `Writer.resume()` 续写 `(seq, chain, prefix)`；且**默认每次运行一个文件**（`-r<run_id>`），天然规避 |
| 分段上传 | 每批带 `X-Fwlog-Chain-Before`（批前一帧的链值）⇒ 批次可独立验证；或整文件顺序验证（文档已明确二选一） |
| 性能（实测） | 加密 **4,578 帧/秒**（含内容链）、解密+验链 **37,828 帧/秒**；**每回合 ≈ 0.11 ms**，占 5 秒红线 **0.002%** |
| 体量（实测） | 真实负载 **4.08 帧/回合**、**596 B/帧** ⇒ 半场 5300 帧 = **3.16 MB**（gzip **1.29 MB**）；100 场 = **1.26 GB / gzip 0.52 GB** |
| 落盘是否阻塞决策 | **参考实现是同步密封**（每回合 0.11 ms，可忽略）；"异步 writer"是**可选优化**，**当前尚未实现**——本版不再声称已具备 |

## 1. 设计目标与约束

### 1.1 目标

1. **可分析**：能自动回答"这一分为什么丢了"——必须记录**决策的候选、期望值、被选者**，以及**下回合的真实结果**（后悔值归因，见 §4.3）。
2. **可回溯**：任意一条 KPI 都能追到具体回合的具体事件。
3. **双方共用**：同一套接口、同一份代码、同一个存储位置；对手无法读我们的日志。
4. **零阻塞**：写日志绝不能拖慢 5 秒响应（判题器红线）。
5. **崩溃安全**：进程被 kill 或重启后，**已落盘与后续追加的帧都必须可解析**（v1.1 修复）。
6. **零依赖**：参赛环境不保证第三方库（本机实测 `cryptography` / `pycryptodome` / `jsonschema` **都不存在**）。
7. **体量可控**：1300 回合不能写出几百 MB（实测单半场 3.16 MB）。
8. **可校验**：提供能跑的 `verify`，而**不是纸面契约**。

### 1.2 硬约束（来自比赛）

- 接口文档：选手程序是 HTTP server，判题器每回合发一次 POST，**5 秒内必须响应**；连接建立 10 秒。
- 沙盒环境**无法访问外部网络** ⇒ 日志**必须本地先落盘**，有网络时再上传；不能依赖实时上报。
- 1300 回合 × 双方 × 上下半场。

## 2. 威胁模型

| 角色 | 能看到什么 | 我们要求 |
|---|---|---|
| **对手队伍** | 共享日志接口/共享存储里的**全部字节**（主要威胁） | 只能看到密文与头部索引；**无法解出任何策略信息**（blob 也已加密） |
| 平台运营方 | 同样是密文；**不需要也不应该持有密钥** | 平台侧零信任：只做不可见的中转/存储；靠 `(run_id, count, first/last_chain)` 回执做完整性锚 |
| 吃瓜观众 | 同平台 | 同上 |
| 持有我们 tar 包的人 | **可以提取主密钥**（见 §6.2 与下方"关键前提"） | ⚠️ 这是本设计的**单点前提**，见下 |

### 2.1 ⚠️ 关键前提（必须由用户确认，不能默认成立）

**本方案的全部机密性 = "除我方与平台评测流程外，没有第三方拿到我们的 tar 包"。**

- 打包时密钥必须随包注入（平台只给端口，无法注入环境变量），而"从 tar 里取密钥"的成本**接近零**
  （实测：解包 + `grep -raE '[0-9a-f]{64}'`，甚至能从 `__pycache__/*.pyc` 的常量表里直接读出）。
- 平台**必然**持有我们的 tar；只要它在评测 / 申诉 / 复盘 / 制品库 / 内部共享盘的任一环被第三方看到，该 build 下**所有** match/instance/half 的日志密文一次性失守。
- **对策（三选一，需用户拍板）**：
  1. **运行时由平台下发密钥**（最干净，取决于平台能力）；
  2. **日志延迟上传 + 赛后离线解密**：进程内只用一次性**公钥**封装密钥，私钥只在我方手上（推荐，且不依赖平台配合）；
  3. 维持现状但**明确降级为"混淆级"**，并在 §11 登记为待确认项。
- **本版文档的立场**：不假装这是密码学保证。**取 (1) 或 (2) 之前，日志机密性等价于"平台不泄漏我们的包"。**

### 2.2 明确不防的

进程内存被 dump；平台主动读取容器内文件；**对日志的整文件删除**（见 §7.3）。

## 3. 日志接口（双方共用）

### 3.1 三个平面

```
① 采集面（进程内）   agent 代码 → FwlogWriter.append(event, **fields)      # 同步密封，每回合 ~0.1 ms
② 落盘面（本地）     logs/fwlog-<build>-<match>-<team>-<role>-h<half>-r<run>.jsonl   # NDJSON，一行一帧
③ 上报面（可选）     sink = file | http                                      # 断网可用；有网再传
```

**默认「一次运行一个文件」**（文件名带 `-r<run_id>`）：崩溃重启后是新文件、新链、新 nonce 空间，
从根上避免"同一文件里两条链"的问题（v1.0 的严重缺陷之一）。需要单文件连续时用 `checkpoint/resume`（§5.4）。

### 3.2 上报面契约（`sink: http`，双方共用）

```http
POST {log_sink_url}
Content-Type: application/x-ndjson          # 或 application/gzip
X-Fwlog-Schema:     fwlog.frame/1
X-Fwlog-Kid:        <kid>                    # 上下文指纹（用于识别用错密钥，不是身份凭据）
X-Fwlog-Bid:        <bid>                    # build 指纹（供平台归属与排障）
X-Fwlog-Team:       <team_id>
X-Fwlog-Match:      <match_id>
X-Fwlog-Instance:   <instance_id>
X-Fwlog-Half:       <half_no>
X-Fwlog-Run:        <run_id>                 # ★ v1.1：幂等与防重放的关键
X-Fwlog-Seq-From:   <第一帧 seq>
X-Fwlog-Seq-To:     <最后一帧 seq>
X-Fwlog-Chain-Before: <批前一帧的链值 base64url>   # ★ v1.1：让批次可独立验证
X-Fwlog-Anchor:       <终结锚 JSON（仅最后一批）>
Authorization: Bearer <team_token>           # 与身份绑定，防伪造写入

Body:  逐行 frame JSON（严格顺序，不可重排）
Reply: {"code":0,"data":{"accepted":5300,"from_seq":1,"to_seq":5300,"run_id":"..."}}
```

- **成功判定必须看业务码**：`{code:0}` 才成功；HTTP 200 + `code!=0` 一律按失败处理（J1 类事故的根因就是只看 HTTP 状态）。
- **幂等键 = `(match, team, instance, half, run_id, seq_from, seq_to)`**（v1.1 加入 `run_id`）；
  平台按该键去重 ⇒ 重传不产生重复数据，**重放旧 run 也不会掩盖新 run**。
- **平台侧零信任**：平台只按头部建索引并原样存储，**不需要密钥**；`X-Fwlog-Anchor` 让平台在无可解密能力的前提下也能发现"被替换/被截断"。
- 断网时 `sink: file` 写本地目录，之后由 loop 的 `fetch-logs` 取回，格式完全一致。
- **日志回流通道必须在 Phase 0 定义清楚**（见 `02` §4.4）：若平台无日志下载接口，就必须约定容器内文件如何取出（挂载卷 / 制品回传 / 平台内置的文件浏览），否则第 7 环"获取日志并分析"没有输入。

### 3.3 文件命名

```
logs/fwlog-<build_id>-<match_id>-<team_id>-<role>-h<half>-r<run_id>.jsonl        # 一次运行一个文件
logs/fwlog-....jsonl.gz
logs/anchors/<match>-<team>-<instance>-h<half>-r<run>.anchor.json                # 终结锚 sidecar
logs/blob/<sha256[0:2]>/<sha256>.fwl.jsonl                                       # ★ 加密的大对象（单帧），无明文
```

- `blob` 的**文件名**是**明文 payload 的 sha256**（用于内容寻址/去重），**内容**是加密帧。
  文件名只泄漏"某个哈希存在过"，不泄漏内容；若连这点也不接受，可改用密文哈希命名（代价是失去去重）。

## 4. 事件模型（`fwlog.event/1`，加密后的明文负载）

### 4.1 公共字段

```jsonc
{ "schema": "fwlog.event/1", "ev": "<事件类型>", "round": 85 }
```

`round` 语义：**事件发生时所处的回合**；半场收尾事件（`stat`/`bye`）取"最后一回合 + 1"（1300 回合的半场 ⇒ `round = 1301`，schema 已放开上限）。

### 4.2 事件类型表

**原则：只记录"分析必须用到的"字段；能被原始 payload 复算出来的不重复记。**

| `ev` | 何时写 | 关键字段（**与 schema 一致**） | 分析用途 |
|---|---|---|---|
| `boot` | 启动一次 | `build, side, cfg_hash, py` | 复盘"是不是版本/配置不对"。**v1.1 修正**：不再声称有 `run_sh_argv`/`q_limits`（没有落地通道）；运行信息进 `cfg` 事件 |
| `cfg` | 启动一次 | `config`（**必须包在 `config` 键里**，阈值/权重全量快照） | 参数搜索时对齐配置 |
| `round` | 每回合 1 条 | `phase, gold, score_total, station_hp, robots_n, robots_by_type, tower_levels, wall_alive, decide_ms, cmds_n, errors_n, retry_of_round` | 全场 KPI 时间序列（主力事件） |
| `cmd` | 每回合 1 条 | `cmds:[{unit, action, name, num, targetPos, controller, taskAnswer, item}]` | 指令级回放、非法率统计 |
| `ack` | 每回合 1 条 | `results, treasure_result, new_errors, last_cmd_result{exit_code,timeout,judger_error,truncated,out_head}` | **唯一合法性反馈通道** |
| `guard` | 每次自检丢弃/改写指令时 | `rejected:[{unit, action, reason, detail}]` | 合规率、`build name` 猜错等问题的即时发现 |
| `decision` | 关键决策 | `dkind, module, chosen, cands`(**≤3** 条), `why, fallback` | **后悔值归因**（§4.3） |
| `outcome` | 决策的下回合结算 | `dkind, module, matched, dmg, kills, gold_delta, hp_delta, score_delta` | 把"期望"与"实际"配对 |
| `task` | 任务状态机迁移 | `task_point, task_type, phase, timeout, deadline, pass_rate, answer_hash, score_gained` | `score_1` 归因、耗时分布 |
| `sandbox` | 用了 `executeCmd` | `cmd_hash, cmd_head(≤256B), exit_code, out_head(≤256B), truncated, timed_out` | SOP 复用、沙盒行为学习 |
| `econ` | 采集/贩卖/购买/升级 | `kind, item, num, price, gold_before, gold_after, target` | 经济曲线、买卖决策质量 |
| `combat` | 每晚汇总 1 条 | `shots, dmg_by_tower, kills_by_type, overkill, idle_tower_rounds, robots_in_range` | `score_2` 归因 |
| `news` | 世界新闻变化时 | `official_hash, official_head, folk_hash, folk_head, price_snapshot` | 推理类/宝藏推断的可追溯性 |
| `anomaly` | 异常/兜底/超时 | `kind, exc_type, tb_head(≤512B), fallback_used` | **P0 合规红线**监控 |
| `stat` | 每半场结束 1 条 | `s1, s2, s3, total, kills, tasks_done, tasks_failed, uptime_days, base_alive, enemy_score, winner` | 半场汇总 = scoreboard 行 |
| `bye` | 进程退出 | `reason, rounds_seen, frames_written` | 完整性对账 |
| `payload` | blob 单帧文件 | `sha256, enc: "gzip"` + 原始 payload（密文） | 异常回合的全量现场 |

- **`frames_written` 语义**：**包含 `bye` 自身**在内的该文件总帧数（样例 = 14）。
- **异常强制全量**：只要本回合出现 `anomaly` / `guard.rejected` / `ack` 中 false，就把该回合的原始 payload 与全量决策写入 `blob/`（不采样）。**这条让"看不见的 bug"无法藏身。**

### 4.3 决策-结果配对（**本设计最关键的一条**）

```jsonc
// 第 85 回合：记录候选与期望值（只记 top-K，K 默认 3）
{"schema":"fwlog.event/1","ev":"decision","round":85,
 "dkind":"attack_target","module":"combat.rocket",
 "chosen":{"u":10040,"aim":[[12,20],[13,21]],"ev":58.0},
 "cands":[{"aim":[[12,20]],"ev":31.0},{"aim":[[13,21]],"ev":22.5},{"aim":[[14,22]],"ev":18.0}],
 "why":"cluster,splash=9,overlap=0"}

// 第 86 回合：结算真实结果 → 自动算出 regret = max(cands.ev) - actual
{"schema":"fwlog.event/1","ev":"outcome","round":86,
 "dkind":"attack_target","module":"combat.rocket","dmg":58,"kills":2,"matched":true}
```

- **为什么值得单独设计**：没有 `decision/outcome` 对，分析只能得出"这局分低了"，**得不出"哪一步决策把分丢了"**，loop 就无法自动产生下一轮假设。
- 体积控制：只对关键 `dkind`（`attack_target / assign_role / accept_task / buy_item / wall_plan / tower_site / sell_batch / treasure_summon / sandbox_cmd / fallback`）记录，且按 `decision_sample` 采样，或"最优与次优期望值差距 < 阈值"（真正纠结的时刻）才记。

### 4.4 采样与分级（体量控制）

| 开关 | 默认 | 说明 |
|---|---|---|
| `level` | `info` | `error/warn/info/debug/trace` |
| `module_levels` | `{}` | 例如 `{"combat": "debug"}` 只放开某个模块 |
| `full_payload_every` | `0`（关） | 每 N 回合把**判题器原始 payload**（**加密后**）存进 `blob/`；异常回合**强制**存 |
| `decision_topk` | `3` | `decision.cands` 保留的候选数（schema 上限 8） |
| `decision_sample` | `1` | 决策事件采样间隔 |
| `max_frame_bytes` | `8192` | 超长自动截断并打 `truncated:true` |

## 5. 帧格式与加密方案（v1.1）

### 5.1 帧（一行 NDJSON）

```jsonc
{"h": {                        // 头部：明文，作为 AAD 参与认证
   "magic":"FWL1","v":1,
   "alg":"hmac-aead-v1",       // 或 "aes-256-gcm"
   "kid":"e3a819177678f61c",   // ★ 上下文指纹（用错密钥/错上下文时用于诊断；不是 build 指纹）
   "mid":"M-2026-DEMO-001",    // match id
   "tid":"6324",               // team id
   "inst":"challenger-node-a", // 实例 id（自对弈时区分双方）
   "run":"rdemo0001-00000000", // ★ v1.1：运行实例 id（参与密钥派生与链起点）
   "half":1,                   // 上半场/下半场
   "seq":2,                    // 单调递增，从 1 开始
   "round":85,                 // 游戏回合
   "ts":1767225600000,
   "ev":"round","lvl":"info",
   "n":"3q2-7wAAAAAAAAAC",     // 12 字节 nonce（base64url，**规范编码**）
   "chain":"BaYcG6NVVMtAhFF3koCFAg"  // ★ **上一个**链值（第 1 帧 = chain_start(run_id)）
 },
 "c":"<base64url(密文)>",
 "t":"<base64url(MAC,16B)>",
 "x":"<base64url(本帧新链值,16B)>"}   // ★ v1.1：内容绑定的累进链
```

- **头的规范化序列化**（键排序、无空格、ASCII）就是 AAD。校验方解析后重新规范化，因此改键序无害、改值必然破坏 MAC。
- **base64 必须规范**：`-`/`_` 字母表、无补位、无空白；解码后重新编码须与原串逐字节相同（否则同一帧有多种字节表示，内容寻址会失效）。
- 头部明确**不含**：坐标、目标、任务答案、LLM 文本、指令内容——全部在密文里。

### 5.2 密码学构造（`hmac-aead-v1`，仅标准库）

```
① 上下文绑定（run_id 也在内）
   ctx   = "fwlog/v1|" + mid + "|" + tid + "|" + inst + "|" + half + "|" + run_id
   salt  = SHA256(ctx)
   okm   = HKDF-SHA256(ikm = team_secret(32B), salt, info = "fwlog/v1 aead|" + alg, L = 64)
   K_enc = okm[0:32] ;  K_mac = okm[32:64]
   kid   = HMAC(K_mac, "KID")[0:8]                       # 上下文指纹
   bid   = HMAC(team_secret, "BUILD" + build_id)[0:8]     # build 指纹（排障/归属）

② nonce（12 字节，绝不复用；**前缀必填，无默认值**）
   nonce = 运行前缀(4B) || 计数器(8B 大端, 从 1 起, 每帧 +1)

③ 密钥流（CTR 模式，PRF = HMAC-SHA256；单 nonce 上限 2^32 块 = 128 GiB）
   block_i = HMAC(K_enc, "KS" || nonce || u32be(i))
   ct      = pt XOR ks[0:len(pt)]

④ Encrypt-then-MAC
   tag = HMAC(K_mac, "MAC" || u32be(len(aad)) || aad || nonce || ct)[0:16]

⑤ 内容绑定累进链（v1.1 的核心修正）
   chain_0 = HMAC(K_mac, "CHAIN0" || run_id)[0:16]        # 绑 run：不同运行的链序列必然不同
   x_i     = HMAC(K_mac, "CHAIN" || chain_{i-1} || u64be(seq_i)
                              || u64be(len(aad_i)) || aad_i || ct_i)[0:16]
   帧头的 chain 字段 = chain_{i-1}；帧尾的 x 字段 = x_i
```

**为什么安全（而不是自创密码学）**：这是标准的 **EtM(PRF-keystream, HMAC-SHA256-128)** 构造，两个原语都是 NIST/RFC 标准原语。
在 **HMAC-SHA256 是 PRF** 的假设下达成 IND-CCA（与 AES-CTR + HMAC 的 EtM 同构，IPsec/SSH 同款）。
**与 AES-GCM 的区别（不含糊其辞）**：① 长度界不同（本方案单 nonce 上限 128 GiB vs GCM 的 2³⁹−256 bit）；
② 本方案为自研组合、**未经第三方审计**；③ 密钥材料按 `alg` 分离（`info` 不同），因此**不存在跨算法密钥复用**。

**为什么不用纯 Python AES**：纯 Python AES-GCM 只有几 KB/s，1300 帧要几十秒，**会直接撞穿 5 秒决策红线**。实测本方案 **4,578 帧/秒**。

**算法可替换但未经实测**：环境若有 `cryptography` 或 `pycryptodome`，把 `alg` 换成 `aes-256-gcm` 即可（帧结构、密钥派生流程一致，仅 `info` 加 alg）。
⚠️ 本机（= 参赛环境）**两者都不存在**，因此**该分支从未被验证**；`open_frame` 遇到"无可用 AES 提供者"会抛干净的 `ValueError`（而不是 `ModuleNotFoundError`）。

### 5.4 崩溃重启与续写（v1.1 修复）

两种模式，**默认用第一种**：

| 模式 | 做法 | 优点 |
|---|---|---|
| **① 一次运行一个文件（默认）** | 文件名带 `-r<run_id>`；重启即新文件、新 `run_id`、新链、新 nonce 空间 | 简单、无状态、天然无冲突；`fwlog merge` 可把同一 half 的多个 run 合并分析 |
| ② 单文件续写 | 每次 flush 后写 `logs/.<file>.ckpt.json`（`{seq, chain, prefix, run_id}`，原子替换 + fsync）；启动时 `Writer.resume(keys, checkpoint)` | 单文件连续；代价是 checkpoint 与日志之间可能有几帧缝隙（**必须记一条 `anomaly(kind=resume_gap)`**） |

- `Writer.resume()` 会**沿用同一前缀并续号**，因此不会复用 nonce、不会断链（自测第 14 项覆盖）。
- 无论哪种模式，`run_id` 都进入 HKDF 上下文 ⇒ **同一 `match_id` 被平台重跑时，两次运行的密钥与链完全不同**，重放/拼接无法互相冒充。

## 6. 密钥管理

### 6.1 三层密钥

```
队伍主密钥 team_secret (32B)                       ← 唯一需要长期保管的秘密
    │ HKDF(ctx = match|team|instance|half|run, info = "fwlog/v1 aead|"+alg)
    ├── 实例密钥(run A, half 1, challenger)  → K_enc/K_mac/kid
    ├── 实例密钥(run B, half 2, defender)    → …
    └── …
```

- **每半场 × 每运行一把**：某一场泄漏不影响其它场；平台重跑也不会得到相同密钥。
- **每个实例一把**：自对弈时两边密钥不同，但都能从主密钥派生 ⇒ 分析端可同时解开两边。
- **对手永远拿不到 `team_secret`** ⇒ 拷走密文也解不开（**前提见 §2.1**）。

### 6.2 运行时如何拿到密钥（打包注入）—— **含必须执行的加固**

比赛由平台执行 `bash run.sh port`，**无法注入环境变量**，因此：

| 优先级 | 来源 | 用途 |
|---|---|---|
| 1 | 环境变量 `FW_LOG_SECRET`（32B hex） | 本地开发 / 自测 |
| 2 | 环境变量 `FW_LOG_SECRET_FILE` 指向的文件 | 本地自对弈 |
| 3 | **打包时注入的 `src/agent/_fwsecret.py`（由 Phase 0 加入 .gitignore）** | 线上唯一可行路径 |
| 4 | 都没有 → **关闭日志（降级为不记）**，绝不因为缺密钥而崩 | 兜底 |

**打包流程必须按下面做（v1.0 的流程有实测可复现的泄密路径）**：

```
1. 读 secrets/fwlog/master.json（首次自动生成；权限 600）
2. build_id = <version>+<git短sha>；生成注入文件 src/agent/_fwsecret.py
3. ★ 先 rm -rf src/agent/__pycache__          （否则旧的 .pyc 里可能残留上一次的密钥）
4. ★ 按 package.include 白名单构造临时目录后再打 tar（不要 tar 整棵树）
5. ★ 打包后断言扫描：tar 内不得出现 64 位 hex 常量、"_fwsecret"、"_FWLOG_" 等标记，命中即 fail build
6. ★ 删除工作区里的 src/agent/_fwsecret.py **以及同名 .pyc**
7. 记录 (build_id → run 级密钥可派生自 master) 到 secrets/fwlog/builds.jsonl
```

**必需的 `.gitignore` 条目**（当前仓库**没有**这些条目，实测 `git check-ignore` 失败）：

```gitignore
secrets/
src/agent/_fwsecret.py
src/agent/__pycache__/_fwsecret*
runs/
loop/state/
logs/
*.fwl.jsonl
*.anchor.json
```

> ⚠️ **v1.0 文档声称"已 gitignore + guard.protected_paths 双重保障"，实测两者都不成立。**
> 本版把它改成**必须执行的动作**，并列入 `loopctl guard check-secrets` 的检查项与 Phase 0 验收项。

### 6.3 轮换与销毁

- **每 build 一把主密钥**，旧密钥保留在 `secrets/fwlog/` 供历史日志解密。
- 比赛结束后 `secrets/fwlog/` 归档进 `runs/<iter>/`，保留至赛季结束。
- `_fwsecret.py` **永不入库**（`.gitignore` + `guard` 双重检查 + 打包断言三重）。

## 7. 完整性：能检测什么、不能检测什么

### 7.1 能力矩阵（**实测**，不夸大）

| 攻击 | 是否可检测 | 靠什么 |
|---|---|---|
| 篡改密文 / 篡改帧头任意字段 | ✅ | MAC（AAD 覆盖整个头部） |
| 篡改 nonce | ✅ | nonce 同时进 AAD 与 MAC 输入 |
| 中间删帧、相邻换序 | ✅ | 内容绑定链 |
| **跨运行拼接**（同 match/team/instance/half，不同 run） | ✅（v1.1 修复） | `chain_0` 绑 `run_id` + 链绑内容 |
| 跨 match/team/instance/half 搬帧 | ✅ | 密钥不同 ⇒ kid 不匹配 |
| 用错密钥 / 错上下文 | ✅（诊断明确） | `kid mismatch`（**校验顺序已改为 kid 优先**，不再误报成"被篡改"） |
| **尾部截断** | ⚠️ **链检测不到**；需 **anchor** | `(run_id, count, first_chain, last_chain)` 锚必须放在文件之外 |
| 整文件删除 / 替换 | ❌ | 靠平台回执对账（§3.2 的 anchor 与 run_id 计数） |
| 持上传凭据者冒名写入 | ❌（只能事后发现） | kid 不匹配会被我方 `verify` 发现；平台侧需 `token ↔ X-Fwlog-Team` 强校验 |

> **诚实结论**：**链能防"改内容"，不能防"删尾巴"**。检测截断必须依赖文件之外的锚（平台回执或 sidecar）。
> 实测：不带 `--anchor` 时 `verify` 会明确打印 "tail truncation is NOT detectable" 的警告，而不是给出虚假的 OK。

### 7.2 `fwlog verify` 的检查项（**已实现**）

`python3 reference/fwlog_crypto_ref.py --verify <file> [--anchor <a.json>] --secret-file ...`

1. 逐帧格式与长度校验（nonce=12B、tag=16B、chain=16B）；
2. `alg` 与密钥材料一致性；AES 不可用时抛干净的 `ValueError`；
3. `kid` 匹配（先于链，保证诊断正确）；
4. 链路归属（帧头 `chain` == 上一帧的 `x`）；
5. **内容绑定链**重算比对；
6. MAC 验证（`compare_digest`）；
7. **序号连续性**（`seq` 必须 +1 递增，可关）；
8. 与 `--anchor` 比对 `count` 与 `last_chain`（**截断检测**）；
9. 输出 `{ok, frames, gap, error, kid, observed_anchor, warning}`。

> **纪律**：任何一帧失败都**不得推进链状态**（参考实现已如此），否则后续帧会全部误报。

### 7.3 脱敏清单（**绝对不能进日志**）

`team_secret` / `K_enc` / `K_mac` / 平台口令与 token；`guard scan-secrets` 命中即判失败。
LLM 原始响应只记 `answer_hash` + 前 128 字节；`executeCmd` 超 256 字节截断。
**`blob/` 与 `samples/` 也在清单内**——样例密钥必须显式标注 `secret_is_demo: true` 并列入扫描白名单。

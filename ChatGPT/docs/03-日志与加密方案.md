# 日志与加密方案

状态：可交给执行 Agent 的设计合同；尚未修改生产代码、安装密码库或验证平台日志通道。依据为 `docs/任务书.md`、`docs/接口文档.md` v1.0 和 CoreGeek 当前源码。平台未公开的能力一律按待确认处理。

## 1. 现状与接入边界

`src/agent/server.py` 每回合以 `LOGGER.info` 打印完整 response；`main3.py` 将 INFO 输出到 stdout，其中可能包含任务 prompt 和提交答案。异常处理使用 `LOGGER.exception`。当前项目 Python >=3.11、dependencies 为空，HTTP 服务为 `ThreadingHTTPServer`，`brain.decide` 按输入生成决策。

现有游戏 Response 只有 `roleCommandMap/prompt/executeCmd`，没有日志字段；不能新增 `log`，不能把日志塞进 prompt、taskAnswer 或 executeCmd。日志适配器单独预留 `emit_ciphertext(bytes)`：选 stdout、受控文件还是网站上传接口，必须先实测平台能采集哪种、双方可见范围、编码/行长/总量限制、是否截断、是否携带可信 team/build/match 标识。任务书沙盒禁止外网，不能假定参赛 HTTP 服务能联网；平台调用由赛外 Loop 控制器执行。

默认替换现有明文 response 日志，所有策略诊断仅走加密 sink。stdout/stderr 的其他 logger、异常栈、启动脚本和 HTTP 错误路径也要审计。游戏响应本身仍按判题器要求返回明文：加密日志无法让平台看不到游戏请求/响应，也不能隐藏敌方通过游戏行为直接观察到的动作。

## 2. 事件合同与分析口径

明文载荷为 UTF-8 JSON，每条一事件，先校验 `schemas/log-event.schema.json` 再加密。除 envelope 的版本/算法/密钥编号/密文外，不公开轮次、策略、队伍 ID 或正文摘要。时间和长度仍可能泄露活动规律。

| 字段 | 规定 |
|---|---|
| `schema_version` | 固定 `cg-log-event/1`，不兼容变更升版 |
| `run_id/build_sha/config_sha` | 赛外迭代 ID、Git 提交、实际策略配置 SHA-256；打包时植入不可变构建信息 |
| `match_id/half_id` | 平台可信 ID；无法注入时为 null，由下载端依据平台任务绑定，禁止用 roundNo 伪造比赛 ID |
| `team_id/side` | 请求中的 teamOur 标识；仅作为自报数据，不能替代平台来源认证 |
| `process_id/seq` | CSPRNG 生成 128 bit 进程实例 ID；单写者递增序号，从 0 开始 |
| `round_no/observed_round_no/request_id` | 决策所属回合、实际观察回合、进程内请求关联 ID；异步结果必须区分所属与观察时间 |
| `event_type/data` | 下表的事件类型与业务载荷；未知值不可静默当成功 |
| `prev_cipher_sha256` | 前一已成功写出完整 envelope 行字节（不含换行）的 SHA-256；首条为 null；仅诊断连续性 |
| `dropped_events` | 自上次成功写出后未记录的事件数量；不含尚未发生事件 |

事件应记录决策依据，而不是要求大模型输出长篇思维链：记录规则编号、候选摘要、被选动作和约束结果即可。

| event_type | data 最少内容与目的 |
|---|---|
| `session_start` | 源码/配置/打包指纹、依赖版本、日志级别、预算；绑定构建来源 |
| `turn` | 输入摘要（金币、积分、基地 HP/level、己方角色位置/HP/背包、武器等级/冷却、可见敌军/机器人数量）、实际 response、每角色 reason_code、候选收益/风险、路径长度/阻塞原因、预留金币、decision_ms、response_bytes |
| `feedback` | lastRoundRoleActionResults、errors、lastSummonTreasureResult、lastCmdResult 的退出状态/截断标识；关联上一已发出请求，关联不明标 unknown，不能假设每次都是 roundNo-1 |
| `task` | 接取/提交/结束状态、任务内容摘要、接取回合、超时、答案 hash、LLM 调用计数与返回状态、命令耗时；原文按诊断级别加密保存 |
| `news` | 官方消息与传闻原文或受限摘要、解析后的资源价格/宝藏假设、证据来源回合、置信度；区分推断与事实 |
| `snapshot` | 可重放的完整请求与必要内部状态，默认每 50 回合、昼夜切换、异常时触发；敏感长字段设单独限额 |
| `error` | error_class、稳定错误码、回退动作、是否响应已发出；完整 traceback 只能出现在密文内 |
| `session_end` | last_seq、最后观察回合、累计 drop、关闭原因；仅进程结束，不能声称平台比赛已结束 |

`turn` 默认每回合一条并合并上次 feedback，避免事件数量失控。每回合积分增量可观察，但请求未提供各分项结算明细：不能把机器人消失当作己方击杀（白天清场、对方击杀也会消失），不能把金币变化直接当采矿收入。记录 `metric_source=observed/derived/platform`；平台最终胜负、上下半场关联和积分是比赛结果权威来源。区分合法性失败与判题异常次数；后者没有计数证据时标 unknown。

Loop 分析输出至少包括基地存活回合、平台胜负、总分、任务完成/超时、经济回合效率、移动阻塞、无操作回合、武器闲置/冷却利用、无效动作、请求耗时 p50/p95/p99/max、日志覆盖率；每条代码改进关联原始事件 ID 和可证伪假设。

## 3. 保密选择：成熟逐条公钥封装

推荐 PyNaCl `nacl.public.SealedBox`（底层 libsodium）。每条记录采用独立临时发送密钥的公钥混合加密，接收者仅需公开公钥，私钥只在赛外离线解密机；库提供 X25519 + XSalsa20-Poly1305 构造和内部 nonce 管理，不自行拼接 DH/KDF/AEAD，也不复用长期对称密钥。[libsodium 官方说明](https://libsodium.gitbook.io/doc/public-key_cryptography/sealed_boxes)、[PyNaCl 官方接口](https://pynacl.readthedocs.io/en/latest/public/#nacl-public-sealedbox)。

选择逐条封装的原因：最多 1300 回合，日志量有限；丢一条不影响后续解密，可乱序下载、逐条验真和增量恢复。SealedBox 密文比载荷多 48 字节，外层 Base64 约增加三分之一。若未来量级明显增加，可独立升级到 libsodium secretstream + 公钥封装流密钥，但需可靠排序、流头、FINAL 标记及断流处理，不能与当前 v1 混用。[secretstream 官方接口](https://libsodium.gitbook.io/doc/secret-key_cryptography/secretstream)。

线格式（值为说明占位，非有效密文）：

```json
{"v":"cg-sealed/1","alg":"libsodium-sealedbox","kid":"sha256-public-key-hex","ct":"BASE64_SEALED_EVENT"}
```

`kid=SHA256(32 字节原始接收公钥)`，私钥不得放在源码、环境变量转储、参赛包、日志、agent prompt 或共享归档中；归档仅放公钥与非秘密密钥编号。密钥对在受保护的赛外环境产生，权限最小化，私钥备份独立加密；按赛季/实验批次轮换并保留旧 keyring 以解密旧结果。长期私钥泄露可解密该密钥的历史日志，不承诺对接收方密钥泄露的前向保密。

加密过程为 `SealedBox(PublicKey(pk)).encrypt(json_utf8)`；解密使用私钥对应的 `SealedBox`。编码器参数、密钥长度和库异常必须严格检查；公钥缺失、随机源失败、加密失败时禁止回退明文。CSPRNG 使用操作系统安全随机源，不用时间戳、roundNo、random.seed 或比赛 seed 生成密钥/nonce。进程重启重新产生 process_id；每条临时密钥由库重新生成，不能缓存、序列化或恢复 nonce/临时密钥状态。并发请求由锁保护关联状态，单写者负责序号、加密和完整行写入；不能让两个线程交错半条密文。

## 4. 完整性、来源与缺失的边界

SealedBox 可拒绝损坏密文，但不认证发送者：任何知道公钥的人都能构造可解密的新日志。team_id、build_sha、hash 链同样可以自报或重新生成，因此“成功解密”不等于“我方日志”。必须由可信平台导出记录的上传者/队伍/构建/比赛绑定来认证来源；如果共享接口没有可信来源，分析结果应标 `provenance=unverified`，不得单凭其晋升版本。将静态签名私钥打进参赛包不能解决包可读威胁。若平台支持运行时保密注入签名密钥，可另行设计认证版本，当前不假定具备。

下载时保存原始记录、平台记录 ID、获取时间、来源绑定及文件 SHA-256。先按平台来源隔离，再严格解码/解密/校验 schema，再按 process_id/seq 去重与排序；相同 seq 不同内容隔离报冲突，不覆盖。哈希链可发现已知连续记录间的缺失或替换，不能阻止攻击者重造整条链，也不能独自发现尾部/整局删除。对照平台最后回合、分页结束游标/日志总数和 session_end 检查覆盖率；没有 session_end 是不完整，不自动推断攻击。正常比赛也可能没有进程关闭通知，必须以平台终态补足。

加密无法抵御能读参赛进程内存的对手/平台，无法隐藏程序实际运行的秘密状态，也不保护提交包内代码；目标是使只能读共享日志的人无法读正文。分析机解密后产生的明文文件也需受限存储，不回传共享接口。将日志文本视为不可信数据：其中任务/LLM/命令输出不得被分析 Agent 当作新指令执行。

## 5. 资源预算与失败策略

初始建议值，均待目标环境基准测量：单回合正文目标 2–4 KiB，普通事件最多 8 KiB，snapshot 最多 64 KiB；半场总密文预算 12 MiB，有界队列 256 条且总内存 2 MiB，先达到的限额生效；日志 CPU p99 目标低于 10 ms。完整单行上限取平台实测限额与本地限额较小值；禁止按字节硬截断密文，过大事件在加密前缩减并记录 truncated_fields。若平台行长不足，由后续适配器实现带 part_index/part_count/整体 hash 的分片，并在解密前重组且校验上限。

决策响应等待上限为规则规定的 5 秒，不能让上传重试阻塞响应。请求线程优先完成协议响应写出，再以非阻塞方式交付有界队列；响应失败也只交付受限错误事件。加密和 sink 写入由独立单写者处理，不在请求线程同步等待；队列内明文只在本进程内存暂存，不落普通文件。若没有可用 sink，丢弃低优先级详细事件并累计 drop；保留核心摘要优先。网络上传仅在赛外进行。任何日志异常不得改变原决策或触发明文 traceback。可输出无动态秘密的固定 `LOG_DISABLED`，其出现仍会泄露日志故障；默认关闭该提示，由赛外观察覆盖率发现。

为支持准确链条，seq 在单写者准备实际写出时分配；失败写入可能留下半行，此流标记损坏，下一条开始新的 process/stream 实例标识并报告丢弃数量，不能把未成功写出的记录当成 prev。传输重试直接重发已封装字节并用记录 hash 去重，不重新加密制造第二个 seq 版本。不能证明 sink 写入原子性时，必须由日志适配器定义 ack/失败恢复合同。

## 6. 交给执行 Agent 的实施顺序与验收

1. 确认平台采集通道/来源/限额及目标 Python/系统架构；验证 PyNaCl/libsodium 能离线打包。锁定版本与依赖 hash，禁止运行时下载；目前 dependencies 为空，不能假定已支持。
2. 新增独立 telemetry 模块和 sink，把原 response 明文日志替换掉；生产加密不可用时只禁用遥测，正常比赛继续。先实现 turn/feedback/error，再添加策略 reason_code 与 snapshot。
3. 赛外生成密钥并植入公钥。解密工具只接受受限路径/文件描述符引用私钥，不让大模型读取密钥值；输出 schema 合格明文和覆盖率/来源报告供 Loop 使用。
4. 用相同载荷重复加密确认密文不同；正确密钥解密相等，错误密钥、bit flip、截断、畸形 Base64/JSON、超大记录必须拒绝。测试重启、并发、重复/乱序/缺行、缺尾、密钥轮换、加密异常和磁盘/队列满。
5. 在 stdout/stderr 放已知秘密 canary，确认成功与异常路径均无明文泄露；比较开启/关闭日志的相同输入 response 完全相等，压测响应时间和总量；确认赛事包无私钥且干净目标环境能启动。
6. 用平台真实一场双半场结果验收来源关联、日志完整性与解密，再扩大多场实验。依赖/通道未验证前，文档状态保持“方案”，不得声称已实现加密保护。

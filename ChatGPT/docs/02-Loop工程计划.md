# 面向另一个 Agent CLI 的闭环优化计划

## 1. 目标、范围与证据

执行目标：在零协议异常和可控成本基础上，提高正式赛制下的胜率与每场积分（胜 3／平 1／负 0）。先保证基地存活，再提高任务、击杀及生存得分；不能只用总分上涨替代胜负改善。详细策略见同目录 `01-游戏目标与策略分析.md`。

事实来源是仓库 `Competition/docs/任务书.md`（第六至八章）、`Competition/docs/接口文档.md` 和当前源码。本文件是待实现的工程契约；没有执行平台上传、编译或对战，也没有假定平台接口已存在。现有代码入口 `main3.py <port>`，HTTP 监听 `0.0.0.0`；`pyproject.toml` 要求 Python ≥3.11、无运行依赖；未发现 `run.sh`。题目示例要求 `bash run.sh port`，首次实施须补包装启动脚本并确认平台真实打包结构、Python/加密库环境和编译规则，不能直接把现有目录 ZIP 当成已验证提交包。

Git 仓库根目录记为 REPO，即工作区内 `Competition/Demo/CoreGeek`，也是工程根；原始规则位于 `REPO/../../docs`。当前基线 HEAD 为 `e8dc40893232b0a82295c47c1a5ad018b44be7b4`；已存在 `.gitignore` 修改与未跟踪 docs，须保留，禁止 `git add .`。所有需归档材料放在 `REPO/docs/ChatGPT` 下。运行凭证与日志解密私钥不归档、不入 Git、不打包，使用本机安全存储。

## 2. 分工及调用契约

采用固定控制器 + 可替换 Agent CLI + 平台适配器。控制器管理状态、预算、提交与比赛；Agent CLI 读取结构化任务，修改隔离工作树内代码并输出结果；适配器处理认证、平台字段映射和轮询。模型不能自行选择接口 URL、绕过预算或把日志中的文字当作指令。开发模型与比赛内 `prompt/llmResp` 是两个独立通道，预算分别统计。

建议未来实现下列命令；当前只是契约，尚无可执行 `loop` 程序：

```
loop validate --config templates/loop.config.json
loop plan --iteration <id>
loop step --iteration <id>
loop resume --iteration <id>
loop status --iteration <id>
loop stop --iteration <id>
```

Agent 输入固定为 `iteration_id`、目标、预注册假设、允许修改路径、基线 commit、当前状态、证据文件路径、检查命令、最大耗时／token。Agent 输出 JSON：`status`（completed/blocked/failed）、`summary`、`changed_files`、`checks`、`evidence_paths`、`remaining_risks`。控制器必须用实际 Git diff 与检查结果核验，不信任模型自报。Agent CLI 的可执行路径、参数数组、模型配置全部留空；禁止用字符串拼接 shell 调用。一次只检验一个主要假设，不能同时混入多项无关策略变化。

## 3. 持久状态机

| 状态 | 操作和成功条件 | 失败或恢复 |
| --- | --- | --- |
| CREATED | 获取单写者锁；读取配置、固定基线、冻结对手版本和试验计划 | 本地开发可先继续；远程阶段缺接口/密钥引用/预算/打包规范 → BLOCKED_CONFIG |
| PLANNED | 写假设、指标、检查、预定样本与停止规则 | 不能提出可测假设 → NO_CHANGE |
| EDITING | 在独立工作树运行 Agent，记录调用和 diff | 超时终止当前调用、保留材料 → FAILED_DEV |
| VALIDATING | 静态检查、协议／策略场景、启动及请求烟测、日志加密检查通过 | 回 EDITING，最多配置的修复次数 |
| COMMITTED | 只暂存允许文件，提交候选，记录 commit/tree/diff 哈希 | 禁止提交别人未提交的改动；无改动 → NO_CHANGE |
| PACKAGED | 从候选 commit 导出白名单，打确定性包、算 SHA-256，解包烟测 | 不包含 `.git`、文档、私钥、凭证、原始日志；失败 → FAILED_PACKAGE |
| UPLOAD_INTENT | 先原子持久化 operation_id、包哈希、预算预留和请求摘要 | 恢复先查操作是否完成，不能立即重发 |
| UPLOADED | 平台确认 artifact/submission ID，绑定包哈希与 candidate commit | 上传状态未知 → RECONCILING |
| BUILD_PENDING | 轮询已有 build ID；只有明确 SUCCESS 才前进 | FAILED 留编译日志；超时记 TIMED_OUT_PENDING，并继续只读查状态 |
| MATCH_INTENT | 为一个完整换边场预留预算并写操作意图 | 同样先核对后重试 |
| MATCH_PENDING | 记录比赛 ID，等待两半场结束及终态 | 失败/取消/超时单独归档，不伪装成负局或有效样本 |
| COLLECTING | 下载两半场官方结果和日志、分页/解压/校验并保留原件 | 结果完成但日志未就绪可重试只读下载；缺损标注，不静默跳过 |
| ANALYZING | 解密验证、生成指标；未达到预定样本则回 MATCH_INTENT | 失败归因后决定修复或停止，不能按结果任意补样本 |
| DECIDED | 依预注册门槛决定 PROMOTED / REJECTED / INCONCLUSIVE | 更新基线指针或保持旧基线 |
| ARCHIVED | 报告、哈希清单、账本、最终状态齐全 | 结束本轮，下一轮必须新的 iteration_id |

所有状态迁移记录 `from/to/reason/utc/actor/state_version`。写临时文件、落盘、原子替换；单机可用带租约的文件锁，恢复先检查锁所有者而非直接删锁；多机必须改成事务存储与 fencing token。持久状态要含 `baseline_commit`、`candidate_commit`、`artifact_sha256`、`submission_id`、`build_id`、每个 match/half ID、尝试次数、预算已花费/预留、下次轮询时间、操作账本与错误分类。`resume` 从最后一次已验证状态继续，不让模型根据聊天记录猜。

对所有会产生提交或费用的写请求，发送前持久化 INTENT，使用稳定幂等键 `iteration_id:operation:artifact_or_plan_hash`。只有平台明确支持时才发送该幂等头。网络断开或响应丢失时，先按该键或可查元数据对账；查到已建对象则复用。平台既无幂等也无可靠查询时进入 `BLOCKED_RECONCILIATION`，由人工核对后继续，不能宣称本地锁能实现服务端 exactly-once。重新点击、Agent 重启、HTTP 超时都不是重发授权。

只读轮询采用指数退避和抖动，遵守 Retry-After；401/403 停止等配置修复，429/5xx 有限重试；终态映射不完整即阻断。编译/比赛超时不会自动认定平台已取消，预算预留在确认终态或人工对账前不可释放。`stop` 禁止发起新写操作；对已在运行的比赛继续只读对账，取消操作仅在接口语义与费用已确认时使用。

## 4. 修改、提交和打包检查

首轮基线先补可重复启动与最小验证。用真实脱敏请求或由接口构造的明确标注 fixture 检查：8 向移动及占位、上下阵营、基地 2×2、黎明/入夜、背包/金币/共享预算、武器操作者唯一性、目标数组长度、任务保活、无效输入安全处理。HTTP 响应必须仍是游戏协议，不混入日志。服务器响应上限是连接建立后 5 秒，建立连接上限 10 秒；本地目标应留安全余量（初始建议 p99 <1 秒，平台实际资源下复验）。沙盒 `executeCmd` 的 15 秒限额与 HTTP 5 秒是不同机制。

候选 commit 完成后从该 commit 导出打包输入，固定路径顺序、时间戳、权限/压缩参数，保存构建工具版本与依赖锁定记录；如需要生成文件，记录生成器版本与其输入哈希，生成物作为包清单成员。归档清单在包外生成，避免清单自引用。解包到干净临时目录启动检查，验证入口/端口绑定和脱离开发工作树仍可运行。加密日志引入第三方依赖时，需确认平台支持或随包提供经批准、固定版本的依赖；不能假定联网安装可用。

“提交代码”在本计划中默认是本地 Git commit；是否推送远端由配置决定。平台上传是独立操作。提升候选使用基线引用更新或正常合并，不对用户原工作树执行 `reset --hard`。拒绝的候选仍保留 commit 和证据，下一轮从原基线开始。

## 5. 多次对战与统计判定

统计单位是**完整上半场＋换边下半场的一场比赛**，不是 HTTP 请求、回合或单个半场。适配器须确认一次“创建比赛”是否已自动生成两半场；若平台只支持单半场，控制器按相同试验块创建两个换边半场并聚合，未凑齐不得算正式比赛样本。建议固定三个对手版本：当前基线、稳健防御型、任务得分型；后两类不存在时留空，不虚构对手 ID。正式评测须先明确可用对手池；可以预注册只含当前基线的受限评测，但报告需限制外推。开发烟测可仅对当前基线。

建议初始计划：冒烟 2 场完整换边赛（只筛崩溃，不作提升证据）；筛选 12 场（每对手 4 场）；最终留出确认 30 场（每对手 10 场，独立于开发/筛选）。这些是待用户预算确认的设计默认值，配置默认关闭平台写入。候选与基线对相同对手／同 seed 各跑一套完整比赛形成一个配对块，因此最终 30 个配对块通常需要 **60 场完整比赛**；与当前基线直接交锋的样本另列，不能伪装成双臂配对。预算按实际上传、编译、比赛创建次数计算，另含冒烟和筛选。

若平台支持 seed，预先固定、候选/基线复用并记 seed；否则在时间窗口内交错执行两版本并随机顺序，明确为非同 seed，不能称为严格配对控制。地图任务阶段、平台版本、对手提交版本变化时分层记录或重新建立基线；不得混入旧环境结果。每场完整上下半场共同构成一个簇，bootstrap 时不能拆开重采样。

主指标：相对固定对手池的每场积分均值差。优先使用平台官方完整比赛胜平负；规则未明确写全含半场平局等组合，缺官方结果且未确认聚合规则时标 unresolved，不能自行补判或计入有效样本。辅助：胜/平/负比例、总得分及任务/击杀/生存分、基地毁灭回合、存活天数、任务通过率与耗时、协议异常次数、动作执行失败率、p95/p99 延迟、token/费用。客户端看不到官方击杀归属或任务通过率时写 unknown；日志推断与官方字段分开。异常次数按官方累计/事件计算，动作失败不能一律计异常。

固定样本结束后对“候选减基线”的配对块积分差做按对手分层 bootstrap，报告均值和 95% 区间；无同 seed 时报告非配对分层区间及更强随机误差限制。提升门槛建议为主指标区间下界 >0 且无硬门槛回归；区间跨 0 为 INCONCLUSIVE，保持基线。30 块并不保证足够统计功效，不能把统计不显著写成无效。筛选阶段只允许淘汰/进入独立确认，不可把筛选数据累计进确认，避免反复查看后停止的偏差。需追加样本时预注册新一轮确认，或先实现预先定义的序贯检验和多重比较控制。

硬门槛建议：无崩溃、无协议错误、无单队累计 5 次异常停调度、完整性验证通过；性能/日志开销不得突破预算。提前停止仅限预算、配置、平台故障或硬门槛失败，不能因为刚好领先就结束。平台故障造成未完成样本按预注册规则补跑，记录全部失败尝试；候选自身崩溃/异常属于候选结果，不得当平台故障剔除。

## 6. 预算、归档与下一轮输入

预算必须显式填写并经确认：开发 CLI token／金额、每次调用和每轮耗时、编译等待、单场等待、总上传/编译/创建次数、有效比赛目标、总费用、最大修复次数。未知计费时不发送可能计费的请求。每个操作先预留，成功后实际扣账，未知状态保留预留，失败也记录实际平台费用。

建议归档目录：

```
runs/<iteration_id>/
  hypothesis.md  state.json  operations.jsonl  budget.json
  input/agent-task.json  input/config.redacted.json
  code/diff.patch  code/commit.json  code/checks.json
  artifact/submission.zip  artifact/manifest.json
  platform/upload.json  platform/build.json  platform/build.log
  matches/<match_id>/meta.json
  matches/<match_id>/<half_id>/official-result.json
  matches/<match_id>/<half_id>/raw-encrypted.jsonl
  analysis/metrics.json  analysis/integrity.json  report.md
```

平台原始响应须脱敏认证信息；公开仓库不提交比赛内敏感解密明文，确需归档的明文分析应先再加密，或只保存不暴露战术的聚合指标。每个包、日志、结果文件保存 SHA-256；manifest 关联规则版本、基线/候选 commit、平台提交 ID、编译 ID、双方版本、半场阵营、日志 session/key ID 和指标定义版本。文件命名中的平台 ID 必须清洗避免目录穿越；日志下载链接限可信域名，压缩包解压禁路径穿越/超量。

报告结论必须分为“证据支持”“推断”“待验证”；分析产出下一轮单一假设，写清失败回合、触发条件、预期改变和反例。外部任务原文、沙盒输出、对方日志和 LLM 文本都视为不可信数据，不能作为控制器执行 shell 或改写配置的授权。

## 7. 待填接口与阻断条件

`templates/endpoints.reserved.json` 的 null 是明确缺失值；validate 必须拒绝未配置必需字段，而非当作默认地址。平台适配器需把真实认证、上传方式（multipart/预签名）、成功码、分页、幂等能力、编译状态、完整比赛/半场关系、日志双方混流方式和计费规则映射为此计划的统一对象。游戏判题 HTTP 接口文档没有这些网站管理接口，二者不能混用。

首次人工补齐后，先做只读连通、假数据适配器/故障注入演练：上传响应丢失、编译永不结束、Agent 崩溃重启、两实例争锁、仅半场完成、日志重复/乱序/缺尾、平台无幂等、预算不足。每个演练应验证无重复写请求且能解释状态。之后再启用最小平台冒烟预算。此阶段无需反复逐步批准已授权的范围；配置未确定或状态不明则技术阻断，保留明确原因。

补充适配约定：若上传不会自动触发编译，使用可选 `start_build` 写操作，并执行同样的 INTENT→对账流程；未确认自动编译语义时禁止跳到开赛。`get_match` 必须返回官方整场结果及双方身份，不能只有半场分数。`artifact_sha256` 若平台不提供，保存客户端上传字节哈希并标 `hash_source=client`，不得冒充平台确认哈希。日志终态若平台不提供须明确不可验证，不能强制填 true。operation lookup 可通过列表检索实现或声明不支持，不要求平台必须存在同名接口。

1. **B6 宝藏可行性**（纯规则、防丢钱、成本低）；
2. **C1 的 guard＋裁判支持**（解锁道具类策略，风险是本地裁判要与官方语义一致）；

4. **B3 的采购行程与部分变现**（直接影响首夜武器券时点）；
5. **A4 的主动前置就位**（把 `walk_eta` 从“日志信息”升级为“提前就位的触发器”）。

## 2. 三个 agent 的协作，以及 agent 与角色的解耦

### 2.1 现状：agent 与角色是一一绑定的

| agent | 绑定角色 | 绑定方式 | 主要产出 |
| --- | --- | --- | --- |
| `defense_agent` / `attack_agent` | 防御工（`workers()[0]`） | `policies/roles.assign` 按 unit id 粘性指定；`defense.plan` 只规划该单位 | 态势、工作计划、夜间开火 |
| `economy_agent` | 采矿工（另一个工人） | 同上 | 勘察、售卖时机、采集/售卖计划 |
| `task_agent` / `self_evolve` | 开拓者 | `turn.controllable()` 中 `kind=='pioneer'` | 任务、宝藏、任务结束后的防御协助 |

`engine.compute` 是固定的串行流水线（用药→应急→任务反馈→回防→避险→经济→新闻→开拓者→审查→guard），每个单位每回合最多一个动作，动作之间靠 `reserved` 格子与 `scheduler.arbitrate` 的预留表互斥。**因此“三个 agent 协作”目前是“三个角色 agent 各管一摊 + 中心化顺序”，不是联合调度。**

### 2.2 能力矩阵（来自任务书 4.4 与 `guard.legal`）

| 动作 | 防御工 | 采矿工 | 开拓者 | 限制 |
| --- | --- | --- | --- | --- |
| move | ✓ | ✓ | ✓ | 八方向、一格、碰撞即失败 |
| attack（操炮） | ✓ | ✓ | ✓ | 仅夜间、需站在该炮一格内、一单位一回合只能操一座、炮冷却 3 回合（火箭） |
| build / remove | ✓ | ✓ | ✗ | 仅白天；建墙需背包石头 |
| collect | ✓ | ✓ | ✗ | 背包未满、站在矿一格内 |
| buy / sell / use | ✓ | ✓ | ✓ | 需站在商店/小贩一格内；`use` 需持有对应物品 |
| acceptTask / submitAnswer / summonTreasure | ✗ | ✗ | ✓ | 需在任务点/祭坛一格内 |

关键事实：**开火不是防御工专属**。三座炮由同一操作格覆盖，但只要有第二个单位站在某座炮的另一侧邻格，就能在同一回合同时开火。当前只有一个操作者，浪费的是“齐射窗口”。

### 2.3 解耦后的问题形态

把“角色”去掉后，每回合要解的是一个小规模**带时间窗与承诺的多智能体任务分配**：

```
给定：单位集合 U（3 个，各有位置/背包/血量）、候选任务集合 J（约 10 个：采某矿、卖矿、修某墙、建某墙、买某券、去商店、接任务、开某炮、避险、返岗）
     每个任务 j 有：所需能力 cap(j)、收益 v(j)、预计耗时 d(j)、截止期 dl(j)、是否可中断、是否需要承诺（矿点锁/任务绑定/施工中）
求解：把 U 中满足 cap 的单位分配给 J 的子集（一对一，每单位一回合一个动作），使 Σ 收益（折算到“分/回合”）最大
约束：动作合法性（guard）、格子与操作者互斥（scheduler）、通道互斥（单 prompt）、夜间区域限制、返岗截止期
```

规模很小（3×10），**单回合求解本身不难**（贪心甚至全枚举都在毫秒级）；难的是**承诺、切换成本与信息不完全**，而不是组合爆炸。

### 2.4 调度难点（逐条对照当前代码）

1. **既得承诺不能每回合推翻。** 矿点锁（`mine_targets`）、任务绑定（`task_binding`）、施工半成品、在途券（背包物品）都是“沉没投入”；每回合重新竞价会让工人来回摇摆，反而更慢。→ 需要“承诺期内不出价/不被抢”的机制。
2. **截止期是硬约束，不是收益项。** 夜前返岗（第 70 回合）、任务超时（`timeoutRounds`）、围墙破口（`breach_rounds`）都是“迟一分钟就作废”的约束，必须先进可行性过滤、再比收益。
3. **动作与格子互斥已经有一半基础设施。** `scheduler.ReservationTable` 管金币/塔位/操作者/格子；跨角色调度可以直接复用，但要给它加“角色能力”维度（现在它只认 `roleCommandMap` 的键）。
4. **收益口径不统一（最大障碍）。** 见第 3 节：修墙用优先级 100→20，采矿用 `价格×批量/(批量+距离)`，开火用“伤害+压力+溅射”，任务用 `(分+0.5金)/距离`。**没有同一把尺子就无法跨角色比较**，“联合调度”会退化成“按 agent 顺序抢占动作”。
5. **生成本身有成本。** 12 号把 p95 从 300ms 压回 20ms 是靠在 survey/路径/ETA 上省 BFS；真正的竞价调度若每回合给 3 单位×10 任务算真实路径，会重新逼近决策预算（3s）。可行做法是“粗筛用切比雪夫、精算只对入围前 3 名”。
6. **信息不完全。** 矿余量、机器人目标选择、价格预测都不可精确知道；调度应基于期望值与风险，而不是确定值。`submitted_unconfirmed` 这类证据等级要参与权重。
7. **验证成本。** 现有 140 项测试大量锁定“角色专属契约”（例如 `test_intelligence.py::test_only_defender_collects_stone_from_first_day`、`test_defense_revision.py::test_three_towers_and_adjacent_night_operators_both_sides`）。彻底解耦会同时推翻这些契约与已调好的 gather→service→home 日程，回归代价高且难以归因。

### 2.5 优劣对比

| 维度 | 保持角色绑定（现状） | 三 agent 联合调度 |
| --- | --- | --- |
| 主责单位的连续性 | 好：日程稳定、可解释 | 需要额外滞回才不抖动 |
| 主责单位死亡/复活窗口 | 差：`roles.assign` 只按 id 兜底，计划状态（`defender_cycle` 等）与新单位脱节 | 好：矿工可立即接炮，开拓者可接管售卖 |
| 夜间火力 | 差：只有 1 个操作者，首夜 3 发齐射被摊成 3 回合 | 好：第二/第三单位可对齐射窗口（3 炮 × 20 = 60 伤害当回合落地，而机器人攻击结算在武器之后） |
| 闲置时间利用 | 一般：开拓者已有协助，矿工夜间只有采集/等待 | 好：按“分/回合”把闲置单位投到最高价值任务 |
| 实现与验证成本 | 低（已就绪） | 中高：需要统一收益函数＋调度器＋新测试，且要防抖动 |
| 过拟合/调参风险 | 低 | 高：权重维度上升，本地 fixture 的通道偏差容易被“优化”进去 |
| 失败模式 | “各自为政”造成局部空转（如夜间无人开炮） | 抖动、抢占、承诺被破坏、决策超时 |

**结论：完全解耦不划算，但“有界跨角色调度”收益明确。** 单位能力差异（开拓者不能建造/采集、工人不能接任务）决定了“agent 与角色彻底分离”在规则上就不成立；能分离的是**决策权**——agent 负责出价，调度器负责把单位分配给任务。

### 2.6 建议的分阶段方案

- **S0＝现状**（已完成）：粘性角色 + 固定流水线 + 黑板。
- **S1＝任务板 + 有界跨角色（建议下一步做，收益明确、改动可控）**
  1. 黑板新增 `jobs` 段：各 agent 发布 `{capability, value, eta, deadline, commit_until, reason}`；`value` 先用第 3 节的口径，允许先粗糙。
  2. 调度器只在**三类情形**允许跨角色抢占：① 主责单位不可用（死亡、复活窗口、被任务通道占用）；② 高价值短窗口（夜间首轮齐射、围墙 breach_rounds≤2）；③ 主责单位无事可做且备用任务收益为正（现状已有“开拓者转防御协助”，把它纳入同一机制）。
  3. 保留 `roles.assign` 的粘性主责与既有优先级；抢占必须写日志（沿用 `defense_task_switch` 的 from→to+reason 格式）。
  4. 先做**一个**用例：夜首多单位齐射（第二单位站到某炮的非操作格一侧，只在该炮就绪且基地 3 格内威胁数≥阈值时触发）。该用例可离线量化（每夜首发回合的有效伤害、首夜基地/围墙掉血、机器人入夜后存活数）。
- **S2＝收益竞价**：单位对任务出价（统一收益函数 / 预计回合），贪心＋滞回分配；需要先完成第 3 节的 utility 与日志分解。
- **S3＝全局观察 agent 仲裁**：读黑板给出冲突说明与建议（12 号第 3 节的设计），必要时才升级为建议队列。

## 3. 统一收益函数：把现有决策函数收敛到“分/回合”

### 3.1 现状：五套互不相通的“收益”

| 位置 | 现状口径 | 量纲 |
| --- | --- | --- |
| `attack_agent.aim_value` | 伤害 + 威胁削减（攻击力×紧迫度）+ 溅射加成 | 无量纲混合 |
| `policies/combat._attack_targets` | 字典序（基地距离, 血量, id） | 序数 |
| `mining.candidates` / `economy_agent.survey` | `价格×批量 /(批量 + 2×到矿 + 2×基地距离 + 0.5×小贩距离 + 2)` | 金/回合的近似 |
| `defense_agent.work_plan` | 手写优先级 100→20 | 序数 |
| `pioneer.plan` | `(任务分 + 0.5×金) / (4 + 距离)` | 分/回合的近似 |
| `mining.sell_timing` | 规则分支（六条） | 布尔+理由 |
| `construction.upgrade_order` / `defense` 目标排序 | 字典序 | 序数 |

只有采矿与任务的公式已经是“收益/回合”，但没有共同单位；开火、修墙、用券、放弃任务仍是规则或序数。

### 3.2 统一口径

官方得分结构（任务书第六章）是唯一权威的“价值锚”：

- `score_1 = 任务积分奖励 + 5 × 超时回合数 / (完成回合 − 接取回合)`（部分完成按通过率折减）；
- `score_2 = Σ 击杀机器人积分`（小 1／中 2／大 4／BOSS 10）；
- `score_3 = Σ_{day=1..10} 10 × day × 存活系数`（全存活 550）；
- 金币不是分，而是**投资品**：它只能通过买券/药剂/修复包间接换成分。

因此建议统一为**期望得分增量 ÷ 期望回合数**：

```
U(j | u, t) = [ ΔS_task + ΔS_kill + ΔS_surv + λ_gold · ΔG ] / max(1, E[rounds])
              − C_switch(j, u)
受硬约束：合法性、截止期、单动作、塔冷却、通道互斥、夜间区域、背包容量
```

- `ΔS_*`：期望得分增量（分）。
- `E[rounds]`：该任务预计占用的回合数（含路程，用 `route()` 真实长度；粗筛可用切比雪夫）。
- `λ_gold`：金币的**影子价格**（分/金）。可用“下一件必需品带来的边际得分 ÷ 其价格”估计；`economy_agent.funding_need` 已经隐含这个思路（把“缺多少钱买下一件”作为卖出理由）。
- `C_switch`：切换代价（放弃矿点锁、丢掉任务绑定、在途券、施工半成品），只在抢占时计入。

### 3.3 各项换算（可直接落到参数）

| 项 | 换算 | 备注 |
| --- | --- | --- |
| 击杀 `ΔS_kill` | Σ 机器人积分 × P(该瞄准点使该机器人降到 0 血) | 复用 `attack_agent.aim_value` 的伤害/溅射/超杀模型；**注意分很小**（3 个小型仅 3 分） |
| 生存 `ΔS_surv` | 保护基地＝保住 `score_3` 的剩余部分（第 d 天后剩余 `10×Σ_{k>d} k`，最高 550）＋保住后续所有经济/任务产能 | 建议用**风险项**而非线性：基地被毁是灾难性事件，用 `P(被毁) × 剩余可得总分` 更合适；这样“首夜基地 200 血”和“第 9 天基地 1400 血”不会同价 |
| 任务 `ΔS_task` | `P(成功|家族) × (任务分 + 5×超时/剩余回合预估)`，`P` 由 `memory` 的证据等级给保守值（`verified=False` 时不宜 >0.5） | 速度奖励随剩余回合数非线性放大：**越接近截止，提交的价值越高**，与 `self_evolve` 的停止守卫一致 |
| 金币 `λ_gold·ΔG` | 采集/售卖任务的产出 × λ_gold；λ_gold 由“关键券的边际产出”标定（例：一张武器券 100 金带来每夜多若干击杀与更少破墙） | 只在“钱能买到东西”的窗口有值；钱够用时边际价值下降（分段线性即可） |
| 修缮 `ΔS_surv` 的一部分 | 墙的 `breach_rounds` → 提前修缮＝推迟破口 → 降低 `P(基地被毁)`；同时节省重建石头与动作 | 与 `defense_agent.wall_rows` 的 `incoming/breach_rounds` 直接对应 |
| 避险 | 死亡 = 失去该单位 N 回合产能（复活 20 回合＋丢失位置） | 用“产能损失”折算，而不是固定惩罚 |

### 3.4 参数化、日志与标定

1. **新建 `src/agent/agents/utility.py`**：一个 `Weights` dataclass（建议首批只留 6 个参数）：
   `w_task`、`w_kill`、`w_surv`、`lambda_gold`、`switch_penalty`、`risk_aversion`；默认值全部写注释说明来源（官方公式/任务书表格/工程估计）。
2. **所有 agent 从同一处取参**：`attack_agent`、`economy_agent`、`defense_agent`、`task_agent` 的评分改为调用 `utility.value(...)`；规则分支（硬约束、通道互斥）保持在原处，不进收益函数。
3. **每回合记录收益分解**：黑板新增 `utility` 段与日志行，形如
   `{"kind":"repair_wall","value":0.62,"parts":{"surv":0.9,"gold":-0.1,"switch":-0.18},"rounds":3}`，
   便于回放复盘与参数敏感性分析。
4. **标定流程**：开发种子（1、3）上做坐标上升/小网格 → 在**未见种子**上验证不退化 → 用真实回放（如果平台日志可用）复核 `P(成功|家族)` 与 λ_gold。全程用完整换边比赛为统计单位，不用单半场调参。
5. **单调性测试**：伤害越大收益越高、距离越远越低、`breach_rounds` 越小修缮收益越高、剩余回合越少提交价值越高；再加“权重 ±20% 不改变既有不变量”（例如有可击杀目标时开火仍优先）。

### 3.5 风险与反模式

- **量纲/尺度**：不同项的值域差异大（任务分可达上千，击杀分个位数），必须统一到“分/回合”并检查尺度，否则 `w_kill` 会被迫压到极小。
- **奖励黑客**：收益函数一旦包含“击杀分”，可能出现“为多杀一个小型机器人而放弃任务提交”的次优行为；用 `w_task` 的优先级与硬截止期兜住。
- **本地过拟合**：fixture 的通道偏差（候选多一次命令往返＝每任务约 25 分）会诱使参数去优化“看起来的收益”，必须写明该偏差不可当作真实收益。
- **参数爆炸**：首批不超过 6 个参数；其余保持规则，等有回放证据再加。
- **不要用收益函数替代 guard/scheduler**：合法性与互斥必须是硬约束，收益只用于排序与选择。

## 5. 验证与证据边界（沿用 12 号）

- 规则/协议类改动（B6、C1）用确定性场景＋单测验证；不要用本地 fixture 证明“收益提升”。
- 调度与收益函数类改动（S1、A5、utility）必须给出：同种子同裁判的换边对照、收益分解日志、以及“没有为通过测试而放宽既有不变量”的说明。
- 本地裁判是近似实现，`score_1` 的任务时延项受 fixture 通道偏差影响；真实收益仍以平台回放为准。没有那类证据时写“未验证”。
